# 00. Portfolio World Rebuild — Visual Brief

Status: **DRAFT — awaiting Human Gate 1**
Updated: 2026-09-25

This is the Creative Contract for the Portfolio World v2 rebuild. It is the single reference every skill, agent, and QA pass (`tools/agent-skills/profiles/portfolio-world-visual-qa/`) is checked against. No implementation tuning value from v1 is copied into this document; only the design intent is.

## 1. Product

Portfolio World is **not the game itself** — it is a **walkable portfolio interface**. The user walks a small world to discover:

- Career
- Teaching
- Making
- Gallery

Losing sight of this ranks any world-building decision below the portfolio it exists to present. World fun never overrides portfolio information delivery (carried forward from `retro-harbor-campus-art-direction-v1.0.md` §4: *World = Retro Game Inspired, UI = Modern Portfolio*).

## 2. Theme

**Retro Harbor Campus.** Base visual direction: **Refined Retro Harbor**.

The v1 art-direction record (`reports/portfolio-world/art-direction/retro-harbor-campus-art-direction-v1.0.md`) states this was selected from three compared visual-direction concept images, with Concept Image #1 ("Refined Retro Harbor") as the human-approved base, Concept Image #3 as a secondary reference for environmental richness/life/props, and Concept Image #2 as a structural-readability reference only.

**Fallback record**: this repository and its full git history were searched for the original concept-image binaries (`find` across all files, `git log --all --diff-filter=A` across all commits) and none were found — no PNG/JPG concept-art file exists anywhere in this repository's history. The v1 art-direction document's own written description is therefore the **canonical fallback** for what "Refined Retro Harbor" means:

> Bright, orderly harbor. Stone- and wood-centric. Teal/blue water. A restraint appropriate to a professional portfolio space. A game world that does not read as overly toy-like.

Any future rebuild agent that locates the original concept images (e.g. in an external asset store, a design tool export, or a contributor's local files) should attach them here and this fallback paragraph becomes a supplement, not a replacement — the written characteristics remain binding either way.

## 5. Mood

Required: **Bright, Warm, Open, Welcoming, Creative, Professional, Explorable.**

Avoid: **Dark Pirate Port, Heavy Medieval Fantasy, Horror Harbor, Overly Cute Chibi, Generic AI Game Art, Overdecorated Theme Park.**

## 6. Material Language

Core: **Water, Wood, Stone, Greenery.**
Supporting: **Fabric/Sail, Metal accents, Plaster/facade, Glass/windows.**

Materials must be distinct from each other but read as belonging to one coherent world — no material family may look like it was generated by a different visual system than the rest.

## 7. Reference Policy

Every external visual reference used during this rebuild must record, in the same place it is introduced (a report, a decision entry, or an Art Bible section):

1. What is being referenced.
2. What is explicitly **not** being referenced (the boundary).
3. How it translates into a Portfolio World-specific decision.

"It looks nice" is not a valid reference reason. Direct copying of a specific game's map, sprite, or building design is prohibited — reference for layout principle, density, scale feeling, color inspiration, and landmark usage only (carried forward from `retro-harbor-campus-art-direction-v1.0.md` §24, restated here as a hard rule rather than a soft guideline).

## 8. Composition Rules — Asymmetry, Not a Cardinal Cross

**v1's exact `[N]-[W]--[Plaza]--[E]-[S]` perfect cross is explicitly not the design baseline for v2.** It is preserved only as a documented lesson (§ "Lessons" below), not as a layout to reproduce or lightly modify.

Forbidden:
- A perfect North/South/East/West cross.
- Perfectly centered four-building symmetry.
- Mechanical, grid-plotted town planning.

Preferred, when it reads naturally for a harbor settlement:
- Asymmetrical settlement growth (a harbor town grows around water and terrain, not a compass).
- Offset buildings, varied setbacks from the shoreline/plaza.
- Irregular forecourts — no two destination approaches need identical shape.
- Curved or offset visual routes where the terrain/waterfront justifies it.

**Hard constraint: asymmetry must never cost navigability.** Every destination still needs at least two independent visual cues (per the v1 wayfinding rule, kept: silhouette + sign + path direction + emblem + forecourt + landmark — never color alone). A visitor who is not a gamer must reach any of the four destinations from the hub without guidance. If a proposed asymmetric layout makes any destination harder to find than the v1 cross did, the layout is wrong, not the asymmetry rule.

## 9. Harbor Identity

The first screen must read **"this is a harbor"** immediately, not eventually. Water is not background filler — it must occupy meaningful, substantial visual space, not a decorative strip.

Required:
- A substantial harbor basin (not a thin edge-of-map ribbon).
- A real waterfront relationship to at least one major structure.
- A dock.
- Visible water **negative space** — open water the player can see but not necessarily reach, that reads as "the harbor continues beyond what's playable."
- Warehouse/cargo support.
- Mooring language (posts, rope, buoys — reused from v1's material vocabulary, not its exact prop instances).
- Harbor-life props that make the space feel worked, not staged.

## 10. Fleet Hierarchy

Ships are a **primary visual asset of this world**, not decoration.

- **Tier 1 — Hero Ship.** The main landmark, a scene-composition anchor, the harbor's identity symbol. It must read as the most important vessel in every wide shot it appears in.
- **Tier 2 — Medium sailing vessels.** Visually secondary to the Hero Ship, but still a deliberate presence, not filler.
- **Tier 3 — Small working boats.** Life and scale reference; smallest visual weight of the three tiers.

Vessels are explicitly **not** all the same size or importance. A composition where every boat competes equally with the Hero Ship has failed this rule regardless of technical asset quality.

## 11. Harbor Water Rule — Sheltered, Not Open Sea

**One-sentence test**: *this is the protected water inside a harbor, not the open sea.*

Water must be: **calm, low-energy, broad, soft, rounded.**

Encouraged:
- Small, rounded ripples.
- Subtle reflections.
- Gentle waterline contact between hull and water.

Forbidden:
- Sharp wave peaks.
- Jagged foam crests.
- Open-sea swell.
- Storm-like chop.
- Aggressive whitewater.
- Large, energetic waves around a stationary, moored ship.

**This is a direct lesson from v1's own history, not a hypothetical.** v1's final vessel water-contact fix (`harbor-vertical-slice-final-independent-recheck.md` and the ART-09/ART-10/ART-11 sequence on `feature/portfolio-world-concept-vertical-slice`) used an irregular, jagged wave-crest raster to show hull submersion — a treatment that was independently judged acceptable at the time under v1's *own* water-material direction, but that same jagged-crest energy is exactly what §11 of this brief now forbids for a *sheltered harbor*. v2 must solve "does the hull look like it's sitting in water" with calm, rounded contact language, not v1's sharper crest — no v1 tuning value is carried forward regardless.

## 12. Ground / Plaza Rule — Surface Texture, Not Repeated Objects

In the normal gameplay camera: **STONE = surface texture, never STONE = repeated large objects.**

Rules:
- Fine-grained paving.
- Stone unit subordinate in visual weight to the player, benches, and lamps — never competing with them.
- Low, not zero, repetition visibility — some repetition is inherent to tiled ground; it must not be the first thing a viewer notices.
- Macro surface read first; micro stone detail second.
- No giant paving blocks that individually compete for attention.

**Exact numeric scale (tile size, texture scale factor) is explicitly not locked here.** v1 needed three iterative human-feedback rounds to correct its plaza tile scale (`0.9` → `0.72` → `0.42` across ART-07/ART-09 on the historical branch) precisely because a number was chosen without first validating it against this qualitative rule at actual gameplay scale. v2 must validate the qualitative rule (§ this section) against a real render *before* any scale number is treated as final — see `01_ART_BIBLE.md` for the validation step this maps to.

## 13. Lessons From v1 (design lessons, not implementation values)

Carried forward as constraints on *process*, not as numbers to copy:

1. **Water language must match the water's actual context** (sheltered harbor, not open sea) — a treatment that reads as acceptable in isolation can still violate the world's own stated mood; check against §11, not against "does this look like water."
2. **A surface material's scale must be validated against fixed-size props (benches, player, lamps) at actual gameplay zoom before being called final** — not against how it looks at source-image zoom, and not corrected iteratively after human complaint when a native-scale check up front would have caught it once. See §12 and `01_ART_BIBLE.md`.
3. **"Value changed," "test passed," "build passed," "pixel diff exists," and "effect is technically present" are never, individually or combined, sufficient proof that the normal gameplay render actually looks right.** Every visual claim requires an opened, inspected screenshot of the actual rendered output, judged against this brief. This is the exact discipline built into `tools/agent-skills/profiles/portfolio-world-visual-qa/SKILL.md`.
